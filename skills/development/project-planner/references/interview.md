# Focused discovery

Read the brief, existing docs, code, build configuration, and tests first. Ask about uncertainty that changes the result; skip facts already available. Do not impose question quotas or require a separate interview for every deliverable.

Useful questions depend on the task:

- Outcome: who needs what, what success looks like, and which scope is explicitly excluded.
- Constraints: existing system, chosen stack, deployment/OS/chain targets, external contracts, budget or deadlines.
- Behavior: primary flow, roles, data ownership, and failures that matter.
- Operation: scale, freshness/latency expectations, recovery needs, privacy and release process.
- Learning, if requested: current knowledge, desired depth, and time available.

Keep each turn easy to answer, often one to three related questions. Offer a justified default when useful. A preference that can be reversed cheaply may be labeled as an assumption; a material unresolved choice stays open with its affected work identified.

Summarize consequential decisions when helpful; do not demand confirmation of every inference before drafting. An explicit user review gate remains a gate, but a request to deliver a full plan needs no additional stage approvals.

For a long or interrupted interview, save concise answers, assumptions, pending questions, and next steps in the project's existing memory or an optional planner state file. Reuse it on resumption. Remove only obsolete temporary notes owned by this workflow after preserving useful decisions; do not delete unrelated state.
